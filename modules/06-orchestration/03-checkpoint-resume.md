# 06.3｜检查点、恢复与重试边界

**学习目标：** 理解持久化检查点能保证什么，以及它不能自动保证什么。

Checkpoint（检查点）保存已完成的阶段与恢复所需数据。示例用 SQLite 在每次状态转移时提交 `stage` 和 `data`；重新创建 `Workflow` 对象即可从最后已提交阶段继续。未提交的并行取证若中途失败，会从 `routed` 重做。取证应是只读或可安全重试；有副作用的工具不能直接套用这一策略。

Retry（重试）应限定在已知的暂时性错误，并有次数上限。示例仅对 `TransientSourceError` 再试一次。超时、权限拒绝、格式错误与未知异常应分类处理；盲目重试可能扩大损害。

恢复步骤：读取检查点 → 校验版本和输入 → 判断阶段是否已提交 → 继续下一阶段 → 对外部副作用查询台账。若流程定义改变，旧检查点可能无法兼容，应显式迁移或拒绝恢复。

**实践任务：** 在 `routed` 后注入持续来源故障，关闭并重新打开数据库，再恢复；记录取证次数与最终状态。

**验收标准：** 已提交的取证不会因重新打开而再次调用；失败的取证可以重试；同一运行 ID 不接受不同请求。

**失败案例：** 仅有数据库检查点而外部邮件已发出，崩溃后仍可能再发一次。需要目标系统支持幂等键，或使用可对账的 Outbox（发件箱）模式与补偿流程。
