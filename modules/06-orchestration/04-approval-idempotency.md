# 06.4｜人工审批、幂等与补偿

**学习目标：** 设计真正会暂停的审批边界，并验证重复恢复不重复写入。

Human-in-the-Loop（人在回路中）不是在提示词里写“请先征得同意”。示例在 `waiting_approval` 停住，调用方必须显式提交 `decision` 和 `reviewer`，拒绝则结束且没有报告。教学代码只记录审核者字符串；生产审批还须验证身份、操作范围、审批对象版本、有效期和审计记录。

Idempotency（幂等）指同一个逻辑操作重复请求后，最终效果与一次执行相同。示例的 `reports.run_id` 是唯一键；报告写入与状态转为 `done` 放在同一个 SQLite 事务中。提交后模拟崩溃，再恢复会看到 `done`，报告数量仍为一。这只覆盖同一数据库内的写入。跨数据库、邮件或第三方 API 无法依赖本地事务获得同样保证，应使用目标端幂等键、Outbox（发件箱）、对账和必要的 Compensation（补偿）。

审批不能“自动重试为批准”；过期或重复的审批请求应拒绝。若审批后资料变更，需重新评估并重新审批，而非沿用旧批准。

**实践任务：** 分别批准和拒绝两个运行；对批准路径在写入后模拟崩溃并重新打开数据库。

**验收标准：** 审批前无报告；拒绝后无报告；重复恢复只有一份报告；过期审批被拒绝。

**失败案例：** 写报告成功但状态更新失败，若两者不是一个事务，恢复时可能写第二份；唯一键只能减少重复，仍需保证写入内容和运行 ID 的关系正确。
