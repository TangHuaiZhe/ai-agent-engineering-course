# 02.4｜成本、延迟与质量：如何选择模型和验证改进

## 1. 不要仅凭 Demo 选择模型

同一个模型在简单格式抽取、复杂规划、工具选择和长文证据核验上可能有不同表现。模型比较至少要控制：测试集、调用时间、Prompt、工具版本、采样设置、预算与评分方式。

## 2. Token 预算是系统设计问题

简化的费用计算方式：

~~~text
总费用 ≈ 输入 Token 数 × 输入单价
       + 输出 Token 数 × 输出单价
       + 工具/API/存储等其它成本
~~~

具体单价、缓存折扣、推理 Token 的计费规则和上下文限制因模型与时间变化而不同，应该以对应模型官方价格页和 API Usage 为准，不在课程中硬编码价格。

延迟不仅取决于模型响应，还包括：

~~~text
端到端延迟 = 模型响应 + 工具等待 + 重试/退避 + 排队与网络 + 应用处理
~~~

并行工具调用可以减少部分等待时间，但可能带来竞态和额外成本。

## 3. 最小评测设计

建议先固定至少 20 个案例，每条记录：

| 字段 | 说明 |
|---|---|
| case_id | 稳定 ID |
| input | 任务与来源 |
| expected | 预期的结构或事实 |
| source_truth | 已核验的原始证据 |
| model_id / prompt_version | 真实使用版本 |
| response | 原始模型输出 |
| validation_result | 格式与业务规则结果 |
| latency_ms / token_usage | 实测指标 |
| notes | 错误分类及缺失证据 |

常见指标：

- **Schema pass rate**：通过结构校验的输出占比。
- **Factual accuracy**：与可核验证据一致的占比。
- **Tool argument validity**：工具参数正确率。
- **Task success rate**：端到端完成率。
- **Latency / Cost**：时间与实际计费（报告均值及分布）。

避免“让同一个模型直接给自己的输出打分”成为唯一验收方法。

## 4. 回归实验

当 Prompt 从 v1 改为 v2 时：

1. 保持数据集与评测规则不变。
2. 分开统计成功、失败、跳过以及拒绝回答的样例。
3. 不只看平均分，查看新增错误是否属于高风险类别。
4. 如果版本有新工具权限，需要增加对应的红队案例。

## 小结

Prompt 提升任务表达质量；Structured Outputs 降低格式错误；确定性规则保护业务边界；**Evals 决定修改是否真正有收益**。
