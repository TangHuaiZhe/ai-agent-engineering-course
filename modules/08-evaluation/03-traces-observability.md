# 08.3｜轨迹、步骤片段与故障定位

**学习目标：** 从一次失败追到具体步骤，同时控制日志中的敏感内容。

Trace（调用轨迹）连接一次端到端运行；Span（步骤片段）记录其中的路由、工具调用和答案合成。共享的 `trace_id` 和父子关系可帮助重建执行路径。实验为每个案例与版本生成独立轨迹，记录步骤名、状态、耗时及安全元数据。它借用了 [OpenTelemetry 的轨迹概念](https://opentelemetry.io/docs/concepts/signals/traces/)，但不是该协议的完整实现，也没有导出到观测平台（2026-11-24 核对）。

当一条案例失败时，先看评分原因码，再沿轨迹判断是路由错误、工具缺资料、工具故障、引用组装还是评审错误。轨迹不应无差别保存原始提示词、网页内容、密钥或个人信息。实验只保留案例 ID、类别、模拟来源 ID 和状态；恶意工具文本不会进入 Span 属性。

真实系统还需关联请求 ID、配置版本、模型版本、工具版本、检索索引版本及重试次数，并设置保留期限和访问控制。耗时指标要区分排队、模型、工具与后处理。教学代码的微小本地耗时不能作为线上时延基准。

**实践任务：** 为 N05 与 I01 各画一条轨迹，说明候选版的错误分别发生在哪一步；检查轨迹中是否出现原始请求或攻击文本。

**验收标准：** 每条轨迹有共同 ID，子片段指向根片段；错误能定位到步骤；敏感原文不进入属性。

**失败案例：** 只保存最终答案而不保存工具状态，无法区分“工具没返回”与“模型忽略了返回值”。
