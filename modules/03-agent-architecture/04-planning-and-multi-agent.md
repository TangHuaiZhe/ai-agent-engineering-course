# 03.4｜Planning、分解任务与 Multi-Agent 的取舍

## 1. Planning 是什么？

Planning（规划）指选择完成目标所需的一组步骤、它们的依赖关系以及必要的调整策略。但“在 Prompt 中要求先写计划”不等于具备可靠的执行计划。

区分三种模式：

| 模式 | 控制流 | 适合 |
|---|---|---|
| 固定 Workflow | 代码确定步骤与分支 | 财务指标计算、审批流程 |
| Plan-and-Execute | 先提出阶段计划，执行后可调整 | 复杂研究、跨多个数据源排查 |
| Reactive Agent（反应式） | 每次观察后决定下一步 | 动态探索、边试边诊断 |

计划需要经常更新；它是**指导执行的中间产物**，不是任务已经完成的证据。

## 2. 常见编排模式

~~~mermaid
flowchart LR
  A[任务] --> B{可确定流程?}
  B -->|是| C[固定工作流]
  B -->|否| D[受约束单 Agent]
  D --> E{能否独立并行?}
  E -->|能且有收益| F[编排多个 Worker]
  E -->|不能| G[保留单 Agent]
~~~

- **Prompt chaining（串联）**：一个节点处理后交给下一个固定节点。
- **Routing（路由）**：按分类选择处理分支。
- **Parallelization（并行）**：独立任务并发；聚合时处理冲突。
- **Evaluator–Optimizer（评估-优化）**：生成、检查、反馈，必须有明确停止条件。
- **Orchestrator–Workers（编排者-工作者）**：根据任务动态分解子任务。

以上是架构模式，并不强制要求每个节点都是一个完整 Agent。

## 3. 一个反例：无意义的 5-Agent 研究小组

把“读取财报 → 提取指标 → 计算增长率 → 生成表格”拆为 5 个 Agent：

- 增加跨节点 Prompt、上下文传递和成本。
- 无法消除数字不一致、数据未核验问题。
- 如果计算公式是确定的，使用 LLM 算反而更难复现。

更合理的方案通常是：**单 Agent 处理开放性研究决策，确定性代码负责检索适配器、计算、格式化、权限和审批。**

## 4. 何时 Multi-Agent 有意义？

满足至少一项并能通过评测证明收益：

1. 多个问题可以独立调查，例如行业竞争、财务、产品技术三个方向。
2. 不同子任务需要明显不同的工具权限和上下文隔离。
3. 并行能显著改善端到端延迟，且合并成本小于收益。
4. 专门的审核流程可以测量地降低事实错误或漏检。

即使如此，也需要考虑任务分发错误、依赖关系、重复检索、冲突证据与预算膨胀。

## 5. 如何进行合理比较？

不要比“用了 3 个 Agent 的系统更酷”，而要在固定数据集上比较：

- **任务成功率**（正确完成多少个任务）。
- **引用正确率**（关键结论有没有支持证据）。
- **成本 / 延迟**（Token、工具次数和墙钟耗时）。
- **故障率**（超时、卡死、审批失败等）。
- **开发维护成本**（代码复杂度与可调试性）。

### 本讲练习：架构决策记录（ADR）

为“研究一家上市公司过去 5 年的盈利能力和护城河变化”比较两种设计：

A. 固定数据流水线 + 单研究 Agent。

B. Supervisor + 财务 Agent + 行业 Agent + 估值 Agent。

写下：
- 你预期 B 相对 A 能提升的具体指标；
- 哪些检索和计算必须由确定性代码执行；
- B 的新故障模式和风险；
- 什么评测结果会让你放弃 B。
